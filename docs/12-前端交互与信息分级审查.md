# 前端交互与信息分级专项审查

> 续接《11-中期测试问题分析与改进建议》，本篇聚焦前端：信息展示与分级、操作上下文、按钮跳转、可视化。
> 已通读全部 17 个前端源文件（views/layouts/stores/router/api/styles）。

---

## 一、信息分级的结构性问题

### 1.1 合同管理 vs 合同查询：两套口径，用户无从感知 —— P0

两个页面表格列完全相同（编号/名称/客户/状态/起草人/操作），但背后逻辑差异巨大，且**页面上没有任何提示**：

| 维度 | 合同管理 `ContractListView` | 合同查询 `ContractQueryView` |
|------|------|------|
| 数据范围 | 仅"与我相关"（起草/有任务/待分配） | 全量合同 |
| 筛选条件 | 关键字 + 状态（**缺"已取消"选项**） | 关键字 + 状态 + 客户 + 双日期区间 |
| 导出 | 无 | 有 CSV 导出 |
| 操作 | 详情 / 编辑 / 删除 | 仅详情 |

问题：
- 用户在管理页搜不到某合同，换到查询页又能搜到（即测试反馈的"后注册管理员"现象的前端表现），没有范围说明就成了"系统有 bug"的观感。
- 能按日期区间筛选，但**表格里根本没有日期列**——筛完无法核对结果，筛选器和展示信息脱节。
- 管理页状态下拉漏"已取消"；编辑按钮的 `c.drafterId === auth.user?.id` 是裸 `===`（详情页同类判断都包了 `Number()`，此处类型不一致会静默失效）。

**建议**：
- 两页共用一个 `ContractTable` 组件，用 props 区分：范围标语（在标题旁加"我相关的合同 / 全部合同"副标题或 tooltip）、操作列、筛选器集合。
- 表格列重排为信息分级三层：**主信息**（名称+编号合并为一列，名称为主、编号小字）→ **状态层**（状态徽章 + 流程进度微指示，见 §5.2）→ **辅助层**（客户、起草人、开始~结束日期、创建时间）。
- 管理页补"已取消"选项；两页的 `statusOptions`、`statusLabel` 收口到公共常量（目前 5 个文件各复制一份）。

### 1.2 合同详情页：过程信息埋没在表格列里 —— P1

`ContractDetailView` 的五个平铺 Tab（基础信息/流程任务/时间线/版本/附件）把**最关键的过程信息切碎了**：

- 会签意见、审批意见、拒绝原因都藏在"流程任务"表格的"意见"一列——一个被截断的单元格，而它们恰恰是定稿人/审批人最需要看的内容。
- 操作按钮（会签/定稿/审批/签订）挂在"基础信息" Tab 底部一排——用户要先切去"流程任务"看上一步意见，再切回"基础信息"才能操作。
- "流程时间线"和"流程任务"内容高度重叠（一个记录状态变迁、一个记录任务），用户分不清该看哪个。

**建议（与流水线方案 §5.1 配套）**：
- 详情页顶部、Tab 之上放**常驻流程流水线**，当前环节高亮。
- "流程任务"+"时间线"合并为"流程"Tab：按环节分组，每个环节卡片内列出参与人、状态、**完整意见原文**、时间。
- 操作区固定在流水线下方（或右侧栏），与当前环节绑定：轮到我处理时，操作面板直接出现在首屏，面板内分级展示上下文（详见 §2）。

### 1.3 状态徽章视觉编码失真 —— P2

`styles.css:739-754`：
- `COUNTERSIGNED`（待定稿）和 `APPROVED`（待签订）用了**完全相同的绿色** `#e8f5e9/#2e7d32`——两个不同环节视觉不可区分。
- 同一套色值以大写/小写类名**重复定义了两遍**（详情页任务状态用 `status-SIGNED` 大写、合同状态用 `.toLowerCase()` 小写所致），改色要改两处。
- `UserManagementView` 借用合同状态色类表示用户启用/禁用（`status-APPROVED`/`status-REJECTED`），语义错位。

**建议**：抽 `StatusBadge` 组件统一映射；色彩按"流程温度"编码——未开始灰 → 进行中蓝/橙系按环节渐进 → 终态绿（已签订）/红（拒绝）/灰（取消），保证每个状态唯一可辨。

### 1.4 其他页面的信息密度问题 —— P2

- **客户管理**：表单收集 8 个字段（开户行、账号、传真、邮编、备注…），表格只展示 3 个，其余信息**没有任何地方能看到**（无详情页）；且列表硬编码 `size:100` 无分页，第 101 个客户起静默丢失。建议：行展开或侧滑详情展示全字段；补分页。
- **起草合同**：客户下拉同样只取前 100 条，且**自动默认选中第一个客户**——极易误提交错误客户。建议默认空 + 必选校验（校验已有），下拉改为可搜索。
- **操作日志**：`content` 列是拼接的原始串（"CT2024xx 名称 DRAFT -> ASSIGNED"），建议把状态变迁解析成两枚徽章 + 箭头；无模块/时间范围筛选，只有关键字。
- **用户管理**：角色列直接显示 `ROLE_ADMIN` 等编码而非中文名（角色中文名数据就在 `loadRoles()` 里，但没用于列表渲染）。

## 二、操作上下文缺失：弹窗只有一栏 —— P0（交互层面最大短板）

全站 6 处业务操作用原生 `prompt()` 单行输入框完成，操作者**看不到任何决策依据**：

| 操作 | 位置 | 操作者实际需要看到的 |
|------|------|------|
| 会签 | `MyTasksView:43` / `Detail:96` | 合同概述、附件、其他会签人意见 |
| 定稿 | `MyTasksView:80` / `Detail:108` | **全部会签意见**、当前概述（可编辑）、附件 |
| 审批 | `MyTasksView:54` / `Detail:120` | 概述、定稿版本、会签意见、附件清单 |
| 签订 | `MyTasksView:65` / `Detail:131` | 审批意见、合同要素（金额/日期/客户） |

附加缺陷：`prompt()` 单行无法输入多行意见；点取消和输入空串都静默返回，无任何反馈；签订日期被硬编码为"今天"（`new Date().toISOString().slice(0,10)`），用户不可选。

**建议——统一"操作面板"模式（信息分级三段式）**：

```
┌─ 面板头：当前环节名 + 合同名 + 状态徽章
├─ 上下文区（只读，按相关性排序）
│   ① 上一环节的反馈（会签意见列表 / 拒绝原因）—— 最高优先级，默认展开
│   ② 合同概述（定稿时变为可编辑 textarea）
│   ③ 附件清单（可点击预览/下载）
└─ 操作区：多行意见 textarea + 主/次按钮（审批含通过/拒绝双按钮，拒绝时意见必填提示）
```

落地方式：扩展现有 `?tab=` 跳转模式（分配已经这样做了），待办卡片按钮 → `/contracts/{id}?tab=countersign|finalize|approve|sign`，详情页按 tab 渲染对应面板。所有数据接口（detail/timeline/attachments）后端均已具备，纯前端改造。

## 四、模板独立页（细化第 11 篇问题 2 的前端方案）

核心转变：**模板 = 受控的文件资产**，不是侧栏里灌文本。

- **新页面 `/templates`**（独立路由 + 侧栏菜单项），两种视角：
  - 管理视角（`template:manage`）：上传（multipart，复用附件的类型/大小校验文案）、启停、设置**可见范围**、查看下载量。
  - 使用视角（`contract:create`）：卡片网格展示——模板名、说明、适用类型、更新时间、下载按钮。
- **可见范围字段**：`ContractTemplate` 增加 `visibleRoles`（或 `visiblePermission`）字段，列表接口按当前用户角色过滤；管理页用角色多选框配置。
- **起草页改造**：删除"套用模板填充内容框"下拉（`ContractCreateView.vue:116-124`），替换为"参考模板"区块：展示可见模板卡片 + 下载按钮 + 引导文案"下载模板线下拟稿后，作为附件上传"；"合同概述"（改名后）仅填摘要，正文以附件为准。
- 详情页"基础信息"中合同概述区块下方加附件快捷区（当前要切 Tab 才能看到正文文件）。

## 五、可视化设计

### 5.1 合同流程流水线（用户明确要求，P1）

详情页顶部常驻横向节点流水线：

```
●──────●──────●──────◉──────○──────○
起草    分配    会签    定稿    审批    签订
张三    李四    2/2完成  待王五   3人     赵六
```

- **节点状态四态**：已完成（实心+勾，teal）、进行中（高亮描边+脉冲，blue）、未开始（空心灰）、拒绝（红 ×，且从"审批"节点分叉出"已拒绝 → 待重新定稿"的回退支线）。
- 节点下两行小字：环节名 + 摘要（完成人/进度 x/y/待某人）；hover 或点击节点展开该环节的意见全文（即 §1.2 合并后的"流程"Tab 内容锚点）。
- 数据全部来自现有 `detail`（tasks）+ `timeline` 接口，无后端改动；任务到环节的归组逻辑可复用 `MyTasksView` 的 `taskOrder`。
- 同一组件缩小复用于：待办卡片（mini 版，只画点不写字）、合同列表行内进度指示。

### 5.2 列表行内进度微指示 —— P2

合同列表"状态"列扩展为：状态徽章 + 6 段微型进度条（已过环节填充、当前环节高亮、拒绝段红色），一眼看出"卡在哪一步"，不必逐行点详情。

### 5.3 工作台图表 —— P2

后端已有两个现成接口前端完全没用：`GET /statistics/monthly`（月度合同量）和状态分布计数。建议工作台增加：
- 状态分布环形图（点击扇区跳转对应状态的合同列表——与第 11 篇问题 11 的状态子菜单互通）；
- 近 12 个月合同量柱状图。
- 现有四个数字卡片信息重复（"待办任务"和"处理待办按钮"显示同一个数），可合并腾出空间。

### 5.4 时间线视觉升级 —— P2

现"流程时间线" Tab 的每条记录是"状态A -> 状态B"文本。建议：状态变迁渲染为 `旧徽章 → 新徽章`；拒绝/取消等负向事件用红色节点；与 5.1 合并后此 Tab 可降级为"完整审计记录"折叠区。

## 六、组件化与一致性（支撑以上所有改动）

当前 13 个 view 零组件抽象，重复代码已成体量：

| 应抽组件 | 替代的重复实现 |
|----------|----------------|
| `StatusBadge` | 5 个文件中的 `statusLabel` 函数 + 类名拼接 |
| `OpinionDialog` / `ActionPanel` | 6 处 `prompt()`（§2） |
| `ConfirmDialog` | 7 处 `confirm()` |
| `AppPagination` | 4 个文件相同的上一页/下一页块 |
| `ContractTable` | 管理/查询两页 90% 相同的表格（§1.1） |
| `PipelineStepper` | §5.1，三处复用 |
| `constants/contract.js` | statusOptions、statusLabel、taskLabel、taskOrder 的 5 份拷贝 |
| `composables/usePagedList.js` | 每页重写的 load/search/goPage/loading/error 八件套 |

建议引入顺序：先 constants（零风险）→ StatusBadge/Pagination（纯展示）→ ActionPanel（承载 §2 核心改造）→ PipelineStepper（§5.1）→ ContractTable 合并两页。
