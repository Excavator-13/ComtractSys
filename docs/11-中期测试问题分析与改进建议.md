# 中期测试问题分析与改进建议（第二版审查）

> 基于中期答辩测试问题汇总，对代码结构、功能闭环、页面交互逐条溯源。
> 每条标注根因代码位置与建议方案。优先级：P0=流程缺陷/功能不可用，P1=功能闭环缺口，P2=交互与可维护性。

## 一、测试问题逐条分析

### 1. 权限还能新增？新增了也不知道有什么用 —— P1（建议收敛功能）

**现状**：`PermissionController` 提供完整 CRUD，`PermissionManagementView.vue` 有"新增权限"按钮。

**根因**：权限编码的真正消费方是后端 `@RequirePermission("contract:xxx")` 注解（编译期硬编码）和前端 `router.js` / `MainLayout.vue` 里硬编码的权限串。新增一条权限记录后**没有任何接口或菜单会引用它**，纯属无效数据。此外核心权限清单在三处重复维护（后端 `PermissionService.CORE_PERMISSION_CODES`、前端 `PermissionManagementView.vue` 的 `corePermissions`、`DataInitializer.seedPermissions`），已经出现漂移风险。

**建议**：
- 将权限管理页改为**只读目录 + 可编辑名称/描述**：去掉"新增/删除"入口，后端移除 `POST/DELETE /permissions`（或仅保留给未来插件化场景并在页面注明"新增权限需配合代码发布"）。
- 权限列表以 `DataInitializer.seedPermissions()` 为唯一事实来源；前端 `corePermissions` 集合删除，改由接口返回 `core: true/false` 标记。

### 2. 合同模板应改为可上传/可下载的独立页面 —— P1

**现状**：`ContractTemplate` 实体只有 `content` 文本字段；后端仅一个只读接口 `GET /contract-templates`（`ContractController:99`，缓存 enabled 列表）；模板数据只能靠 `DemoDataInitializer` 预置。前端在起草页用下拉"套用模板"把文本灌进内容框（`ContractCreateView.vue:116-125`）。**没有任何模板管理/上传/下载能力。**

**建议**：
- 新增独立"模板管理"页（建议挂在合同菜单下，权限可复用 `contract:create` 查看 + 新增 `template:manage` 管理）。
- `ContractTemplate` 增加 `filePath / originalName / fileSize` 字段，复用现有 `FileStorageService` + `Attachment` 的存储/校验模式（已有 10MB、扩展名白名单逻辑可直接搬）。
- 接口：`POST /contract-templates`（multipart 上传）、`GET /contract-templates/{id}/download`、`PATCH /contract-templates/{id}/enabled`。
- 起草页的"套用模板"改为"选择模板 → 显示模板说明 + 提供下载"，起草人下载后线下编辑、作为附件上传。

### 3. "合同内容"改名"合同概述" —— P2（纯文案）

**位置**：`ContractCreateView.vue:125`（表单 label 与 placeholder）、`ContractDetailView.vue:324`（详情区块标题）、`MyTasksView.vue:80` 与 `ContractDetailView.vue:108` 的定稿 prompt 文案"定稿内容"、版本历史区块。后端字段名 `content` 不必改，仅改前端文案为"合同概述"。需求文档中的术语同步更新。

### 4. 分配时能选自己（点确定才报错）、还能给管理员派活 —— P0

**根因**：
- 候选人接口 `UserService.assignableUsers()` 返回**全部启用用户**（含操作者本人、内置 admin、新注册无权限用户），不按环节权限过滤。
- 前端 `ContractDetailView.vue:224` 只过滤掉起草人：`users.filter(u => u.id !== contract.drafterId)`。
- 真正的校验在确认时才发生：`ContractService.createTask()`（`ContractService.java:251`）检查 `assignee.hasPermission(requiredPermission)`，contract_admin 没有会签/审批/签订权限，所以"选自己→点确定→报错"。
- admin 拥有全部权限，所以"给管理员派活"能成功——这是权限模型允许的，但业务上不合理。

**建议**：
- 后端 `GET /users/assignable` 增加 `permission` 参数，内部用已有的 `UserRepository.findEnabledUsersWithPermission(code)` 查询；前端三个选择区（会签/审批/签订）分别请求对应权限的候选人。这样**选不到不合格的人，错误根本不会发生**。
- 业务规则补充：候选列表排除内置 admin（`SysUser.isBuiltInAdmin()`），或至少在产品上明确"管理员是否参与业务流程"。
- `validateAssignees` 保留作为兜底校验（防接口直调）。

### 5. 小红点显示 3 个、会签完就出现审批待办、刷新不更新小红点 —— P0（本次最核心的流程缺陷）

**根因（一个设计问题引出三个症状）**：`ContractService.assign()`（`ContractService.java:92-94`）在分配时**一次性创建会签+审批+签订全部任务，且全部置为 PENDING**：

1. 小红点 `MainLayout.vue:64` 调 `/statistics/tasks/my`，统计口径是 `countByAssigneeAndTaskStatus(user, PENDING)`——把尚未轮到的审批、签订任务也算进去 → 显示 3。
2. 待办页 `MyTasksView.vue` 按合同分组只展示"当前步骤"，后续任务折叠成小标签（即测试反馈"被收起来了，但不明所以"）→ 页面 1 条 vs 红点 3 个不一致。
3. 会签全部完成后合同状态是 `COUNTERSIGNED`（待定稿），但审批任务早已 PENDING，审批人待办里提前出现"审批"——实际点了会被后端 `requireStatus(FINALIZED)` 拒绝。
4. 红点不随"刷新"按钮更新：`MainLayout` 只在 `route.fullPath` 变化时重新拉取（`MainLayout.vue:69`），待办页内的刷新/完成操作都不触发它。

**建议（推荐方案 A）**：
- **A. 分阶段惰性建任务**：分配时仅保存流程人员名单（新增 `ContractAssignment` 表或在任务上加 `WAITING` 状态），状态机推进时再激活下一环节任务——`countersign` 全部完成时激活 FINALIZE，`finalizeContract` 时激活 APPROVAL，`approve` 全过时激活 SIGN。`PENDING` 永远只代表"现在就该你处理"，红点、待办列表、按钮可用性三者口径自然统一。`resubmit()` 的逻辑（重置 APPROVAL 为 PENDING）保持兼容。
- B. 若不想动表结构：`myTasks` 与 `getMyTaskStatistics` 统一改为"任务类型与合同当前状态匹配"的过滤（COUNTERSIGN↔ASSIGNED、FINALIZE↔COUNTERSIGNED、APPROVAL↔FINALIZED、SIGN↔APPROVED），两处必须共用同一个查询方法，避免再次口径分裂。
- 红点刷新：把 `pendingTaskCount` 移入 Pinia store，任务操作成功后与待办页"刷新"按钮统一调用 `store.refreshPendingCount()`；或简单做轮询（30s）。
- 待办页折叠标签改为明确文案："后续环节（未激活）：审批、签订"。

**连带缺陷（同根因）**：某审批人拒绝后合同变 `REJECTED`，其他审批人的任务仍是 PENDING 却无法操作（`approve` 要求 FINALIZED），红点常驻、待办卡死，直到起草人 resubmit。方案 A 可顺带修复（REJECTED 时挂起其余审批任务）。

### 6. 定稿不完善、待办界面应能看合同信息与上一步反馈 —— P1

**现状**：`MyTasksView.vue` 与 `ContractDetailView.vue` 的会签/定稿/审批/签订全部用浏览器原生 `prompt()` 弹框（`MyTasksView.vue:43,54,65,80`），看不到合同内容、看不到会签意见，定稿只能在一个单行输入框里重写全文。

**建议**：
- 待办卡片的操作按钮改为**跳转合同详情页并打开对应操作面板**（分配已经是这样做的，`handleAssign` 跳 `?tab=assign`，照此模式扩展 `?tab=countersign / finalize / approve / sign`）。
- 详情页为每个环节做内嵌表单面板替代 `prompt()`：
  - **定稿面板**：左侧展示全部会签意见（数据已有，`tasks` 里 COUNTERSIGN 的 `opinion`），右侧 textarea 预填当前概述可编辑，提交调既有 `/finalize`。
  - **审批面板**：展示合同概述、附件列表、会签意见后再给通过/拒绝+意见框。
  - **重新提交面板**：展示拒绝原因（REJECTED 的 APPROVAL 任务 opinion）。
- 后端无需改动，所有数据 `detail/timeline/attachments` 接口都已具备。

### 7. 用户"显示名称"无处填写/修改 —— P1

**根因**：注册时 `AuthService.register()` 直接 `setDisplayName(username)`（`AuthService.java:43`），`RegisterRequest` 没有 displayName 字段；修改入口只有管理员的 `PUT /users/{id}`（需要 `user:manage` 权限），**普通用户没有任何自助入口**。

**建议**：
- `RegisterRequest` 增加可选 `displayName`，注册页加一栏。
- 新增自助接口 `PUT /api/v1/auth/profile`（仅允许改 displayName/phone/email/密码，复用 `UserUpdateRequest`），顶栏用户名处加"个人设置"入口。

### 8. 流程任务应显示得更清晰（工作流） —— P2

**现状**：详情页"流程任务"是按 `createdAt` 排序的平铺表格（`ContractQueryService.detail` → `findByContractIdOrderByCreatedAtAsc`）。

**建议**：前端按 `taskOrder`（分配→会签→定稿→审批→签订，`MyTasksView.vue:16` 已有此映射）分组渲染成横向步骤条：每个环节显示状态（已完成/进行中/未开始）、参与人、意见摘要；与"流程时间线"Tab 可考虑合并为一个工作流视图。

### 9. 所有有分配权限的人都留一条记录、定稿排在最后 —— P0/P2

**根因 1（记录冗余）**：`createAssignTasks()`（`ContractService.java:225`）起草时**给每个有 `contract:assign` 权限的用户各建一条 ASSIGN 任务**；某人完成分配后，其余人的任务被批量改成 DONE +"其他分配待办已关闭"（`assign():86`），全部留在流程任务表里展示。
**根因 2（顺序）**：FINALIZE 任务是在会签全部完成时才创建（`countersign():107`），按 `createdAt` 排序自然排在分配时创建的审批/签订之后 → "定稿排在最后"。

**建议**：
- ASSIGN 改为**单条无主任务**：`assignee` 为空、语义是"等待任一合同管理员认领"，`myTasks` 查询时把"无主 ASSIGN 任务 ∧ 我有 contract:assign 权限"并入结果；完成时写入实际操作人。这同时解决问题 10 的快照问题（新注册的管理员自动能看到/认领）。
- 过渡方案（不改模型）：详情页流程任务过滤掉 `opinion == "其他分配待办已关闭"` 的记录，只展示实际完成人那条。
- 排序：流程任务列表改为按环节序（taskOrder）+ 时间二级排序，与问题 8 的步骤条一并解决。

### 10. 后注册的合同管理员在"合同管理"页看不到既有合同 —— P0

**根因**：`ContractRepository.searchRelated`（`ContractRepository.java:45-49`）的可见性条件是：`我是起草人 ∨ 我是某任务的 assignee ∨ (我有 contract:assign 权限 ∧ 合同是 DRAFT)`。ASSIGN 任务是**起草那一刻对当时用户集的快照**，之后注册的合同管理员在老合同上没有任何任务，而非 DRAFT 状态又不满足第三个条件 → 整页看不到。"合同查询"页走的是无关联限制的 `search`，所以能看到。

**建议**：合同管理员是流程管理角色，可见性应基于权限而非任务快照——把第三个条件改为 `(:includeDraftForAssigner = true)` 即**有 contract:assign 权限可见全部未删除合同**（`countRelatedByStatus` 同步改）。若采纳问题 9 的"无主 ASSIGN 任务"方案，此查询也应以权限为准而不再依赖任务行。

### 11. "合同管理"页应有按状态的下级菜单 —— P2

**现状**：状态过滤只是页内一个下拉（`ContractListView.vue:94`），且选项漏了"已取消"。

**建议**：`MainLayout.vue` 仿照"系统管理"组的写法，把"合同管理"做成可展开组：全部 / 待分配 / 待会签 / 待定稿 / 待审批 / 待签订 / 已签订 / 已拒绝 / 已取消，点击跳 `/contracts?status=XXX`，`ContractListView` 监听 `route.query.status` 初始化过滤。子项按权限显隐（如"待分配"仅 `contract:assign` 可见）。可在子菜单上带各状态数量（`/statistics` 已返回分状态计数）。

### 12. 注册疑似有问题 —— P0（已找到一个确定缺陷）

**缺陷**：`sys_user.username` 有数据库唯一约束（`SysUser.java:18`），但用户删除是软删除（`deleted=true`，行还在）；注册查重只查 `existsByUsernameAndDeletedFalse`（`AuthService.java:36`）。**注册一个与"已删除用户"同名的账号 → 查重通过 → INSERT 撞唯一约束 → 500 错误**，前端只能看到一个莫名其妙的报错。`UserService.create` 同样中招。

**建议**（二选一）：
- 软删除时改写用户名：`user.setUsername(username + "#del#" + id)`，保留唯一约束（推荐，改动最小）；
- 或去掉数据库唯一约束、完全依赖服务层查重（不推荐，并发下有竞态）。

另两个注册相关的小问题：前端注册页用户名没有 `minlength=3` 校验（后端 `@Size(min=3)` 会返回校验错误，但提示体验差）；注册成功后直接跳登录页无任何成功提示。

## 三、改进路线建议（按依赖关系排序）

1. **第一批（流程模型修正，P0）**：问题 5 方案 A（分阶段任务激活）+ 问题 9（无主 ASSIGN 任务）+ 问题 10（权限制可见性）——三者同根，建议一次重构 `ContractTask` 生命周期完成；附带修 B1/B2。
2. **第二批（功能闭环，P0/P1）**：问题 12 注册唯一约束修复；问题 4 候选人按权限过滤；问题 7 个人资料自助接口。
3. **第三批（交互升级，P1/P2）**：问题 6 操作面板替代 prompt（连带 B5）；问题 8 工作流步骤条；问题 11 状态子菜单；问题 2 模板上传下载独立页。
4. **第四批（文案与收敛，P2）**：问题 3 改名"合同概述"；问题 1 权限页改只读目录；B3/B4/B6/B7。

> 第一批改动涉及 `ContractService` / `ContractTaskRepository` / `ContractRepository` / 统计与待办两个查询口径，现有集成测试 `ContractWorkflowTraversalIntegrationTest` 覆盖了全流程遍历，重构后务必先跑通该测试再补"任务激活时机"的断言。
