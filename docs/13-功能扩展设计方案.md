# 功能扩展设计方案：流程回退 / 断点续传 / 邮件通知 / AI 审查

> 续接第 11、12 篇。本篇是四个新功能的设计方案，均基于现有代码结构给出落点。
> 前置依赖：第 11 篇第一批"任务生命周期重构"（分阶段激活）应先完成——流程回退直接构建在它之上。

---

## 一、流程回退：撤回、打回、多轮重做

### 1.1 现状与缺口

当前状态机只有一条单向链 `DRAFT → ASSIGNED → COUNTERSIGNED → FINALIZED → APPROVED → SIGNED`，回退能力只有两个点：
- 审批拒绝 → `REJECTED`，起草人 `resubmit()` 回到 `FINALIZED`；
- **`resubmit()` 有数据丢失缺陷**：直接把旧审批任务 `opinion = null` 复用（`ContractService.java:217`），上一轮的拒绝原因从此消失，审计链断裂。

缺口：起草人不能撤回送审的合同；会签环节没有打回能力（会签意见纯咨询性）；打回只能回到"重新定稿"一个位置；多轮往返没有轮次概念，历史互相覆盖。

### 1.2 核心模型：引入"轮次"（round）

**原则：任务行只增不改写。** 每次回退开启新一轮，旧轮任务全部封存，新轮创建新任务行——多轮、任意环节回退、完整历史三个需求被同一个模型满足。

数据变更（Flyway V+1，三方言同步）：

```sql
ALTER TABLE contract_task ADD COLUMN round INT NOT NULL DEFAULT 1;
ALTER TABLE contract ADD COLUMN current_round INT NOT NULL DEFAULT 1;
-- TaskStatus 枚举新增: SUPERSEDED(轮次作废)、WITHDRAWN(已撤回)
-- ContractStatus 枚举新增: RETURNED(已打回)
```

### 1.3 三种回退动作

| 动作 | 触发人 | 允许时机 | 效果 |
|------|--------|----------|------|
| **撤回任务** `withdraw` | 任务完成人本人 | 下一环节尚无任何已完成任务 | 本人任务 `DONE → PENDING`（旧意见复制到状态历史后清空）；若环节完成事件已触发（如全部会签完→COUNTERSIGNED），合同状态回退一格、撤销已激活的下环节任务 |
| **撤回合同** `recall` | 起草人 | `ASSIGNED` 且尚无人会签 | 合同回 `DRAFT`，当前轮所有任务置 `SUPERSEDED`，重新生成分配待办 |
| **打回** `return` | 会签人 / 审批人 / 签订人 | 处理自己的待办时 | 替代纯"拒绝"：选择打回目标（重新定稿 / 重新起草），填写打回意见（必填）；合同 → `RETURNED`，当前轮未完成任务置 `SUPERSEDED` |

打回后的恢复路径（起草人操作，开启 `round + 1`）：
- 目标=**重新定稿**：修改概述/附件 → 重新定稿 → 直接进入新一轮审批（沿用现 resubmit 语义，但创建新任务行而非复用）。
- 目标=**重新起草**：回到类 DRAFT 编辑态 → 重新走会签 → 定稿 → 审批全流程（人员名单沿用上轮，无须重新分配；如需换人由合同管理员重新分配）。

### 1.4 接口设计

```
POST /contracts/{id}/tasks/withdraw          # 撤回我最近完成的任务
POST /contracts/{id}/recall                  # 起草人撤回合同（回待分配前编辑态）
POST /contracts/{id}/return                  # 打回 { targetStage: FINALIZE|DRAFT, opinion }
POST /contracts/{id}/resume                  # 起草人完成修改后开启新一轮（替代/吸收 resubmit）
```

实现要点：
- 全部走既有 `accessGuard.getContractForUpdate(id)` 悲观锁，杜绝"撤回 vs 下一步操作"并发竞态。
- `requireStatus` 风格的前置校验 + 状态历史记录复用 `recordState`，备注写明"第 N 轮 · 由审批打回至定稿"。
- 审批"拒绝"按钮语义升级为"打回"（带目标选择），`REJECTED` 状态保留兼容老数据，新流程统一走 `RETURNED`。

### 1.5 前端配合

- 第 12 篇的流水线组件增加**轮次徽章**（"第 2 轮"）与回退虚线边（从打回环节指回目标环节）。
- "流程" Tab 按轮分组折叠：默认展开当前轮，历史轮收起但完整保留每个人每轮的意见。
- 操作面板：审批/会签面板增加"打回"按钮（弹出目标环节单选 + 必填意见）；详情页对"我刚完成的任务"显示限时"撤回"入口；起草人在 `ASSIGNED` 早期看到"撤回合同"。
- 待办卡片显示"该合同为打回重做（第 2 轮），打回原因：……"。

## 二、大文件与断点续传

### 2.1 现状

`FileStorageService`：单次 multipart、10MB 硬上限、UUID 落盘、有文件头魔数校验（这点做得好，新方案要保留）。大文件（扫描版合同 PDF 动辄几十上百 MB）会直接被拒，且无任何续传能力。

### 2.2 选型对比

| 方案 | 前端 | 后端 | 评价 |
|------|------|------|------|
| **vue-simple-uploader**（推荐） | `vue-simple-uploader@next`（Vue3） | 自实现 3 个分片接口 | 中文生态成熟、自带暂停/续传/秒传 UI、协议简单（约 200 行后端代码），课程项目最优 |
| tus 协议 | `tus-js-client` / Uppy | `tus-java-server`（me.desair.tus） | 标准协议但 Java 服务端库久未维护，集成 Spring Security 较绕 |
| Uppy + 自定义 | `@uppy/core` | 同自实现 | UI 漂亮但英文生态，定制成本高 |

### 2.3 分片协议设计（配合 vue-simple-uploader 默认协议）

```
GET  /api/v1/uploads/verify?identifier={md5}&filename=…   # 秒传/续传探测：返回 uploaded=true 或已传分片号列表
POST /api/v1/uploads/chunk                                 # 上传单分片(multipart): identifier, chunkNumber, totalChunks, file
POST /api/v1/uploads/merge                                 # 全部分片到位后合并 { identifier, filename, totalSize, contractId }
```

- 新表 `upload_session(identifier_md5, original_name, total_size, total_chunks, uploader_id, status, created_at)`；分片落临时目录 `uploads/tmp/{md5}/{n}.part`，合并后走既有 `StoredFile` 流程入 `attachment` 表。
- **秒传**：`attachment` 表加 `file_md5` 列，verify 命中已存在文件时直接建关联记录，不再传输。
- 合并后做完整 MD5 校验 + 既有魔数校验（对合并后文件首 8 字节执行，逻辑直接复用 `validateFileSignature`）。
- 限额调整：分片 5MB；普通图片仍走老的单次接口；大文件上限提到 200MB（`application.yml` 配置化，连同 `spring.servlet.multipart.max-file-size`）。
- 垃圾回收：`@Scheduled` 每日清理超过 24h 未完成的 `upload_session` 与临时分片目录。
- 前端落点：合同详情"附件" Tab 与模板管理页（第 12 篇 §4）共用同一个上传组件，显示分片进度条、暂停/恢复按钮。

## 三、邮件通知

### 3.1 架构：事件驱动 + 通知表重试，不阻塞业务事务

项目已有成熟的事件模式（`OperationLogEventListener`、`ContractStatisticsCacheListener` 都用 `@TransactionalEventListener`），邮件直接复用：

```
业务代码（已有的 recordState / 任务激活点）
   └─ publish ContractChangedEvent / 新增 TaskActivatedEvent
        └─ NotificationEventListener (@TransactionalEventListener AFTER_COMMIT)
             └─ 写 notification 表 (PENDING)            ← 事务外，发信失败不影响业务
                  └─ @Async MailDispatcher 立即尝试发送
                       └─ @Scheduled 每 5 分钟重试 FAILED（≤3 次）
```

依赖：`spring-boot-starter-mail`；启用 `@EnableAsync` + `@EnableScheduling`。SMTP 凭据走环境变量（演示可用 QQ/163 邮箱授权码），**严禁写进仓库**；`app.mail.enabled=false` 时全链路静默跳过（本地开发/CI 不需要真实邮箱）。

### 3.2 通知场景清单

| 事件 | 收件人 | 内容要点 |
|------|--------|----------|
| 任务激活（轮到你会签/审批/签订）| 任务 assignee | 合同名/编号、当前环节、上一环节意见摘要、**深链** `{前端域名}/contracts/{id}?tab=approve` |
| 打回/拒绝 | 起草人 | 打回人、目标环节、打回意见全文 |
| 合同签订完成 | 起草人 + 合同管理员 | 签订信息、附件清单 |
| 合同临近到期（30/7 天）| 起草人 + 合同管理员 | `@Scheduled` 每日扫描 `end_date`，需在 notification 表做幂等去重 |
| 发送合同附件给客户 | 客户邮箱 | 手动触发：详情页"发送给客户"按钮，勾选附件作为邮件附件发出 |

实现注意：
- `Customer` 表**没有 email 字段**，需迁移补列 + 客户表单补输入框（顺带解决第 12 篇 §1.4 客户字段展示问题）。
- 用户邮箱已有（`sys_user.email`）但注册/个人资料均不强制填写——邮箱为空的收件人静默跳过并在 notification 表记 `SKIPPED`，列入第 11 篇问题 7 个人资料页的引导项。
- 邮件附件直接流式读 `FileStorageService.resolve(storedName)`，单封邮件附件总量限 25MB，超限改为发下载深链。
- 模板用简单 HTML 字符串或 Thymeleaf（已是 Spring 生态，6 个模板工作量很小）；正文中的合同名、意见等**必须 HTML 转义**，防注入。
- 通知表同时服务站内信：第 11 篇的小红点体系后续可从"任务计数"升级为"通知中心"，一张表两用。

## 四、AI 合同审查 Agent

### 4.1 定位与边界

**advisory-only**：Agent 产出的是给会签人/审批人的参考报告，不进入状态机、不能自动通过或打回——这是"安全"的第一原则（human-in-the-loop）。

### 4.2 三段流水线（先确定性、后模型）

```
① 文本提取        Apache Tika（统一处理 doc/docx/pdf；扫描件无文本层时标注"需人工查看"）
② 规则预检（零成本、确定性）
   - 结构完备性：必备条款关键词扫描（标的/价款/履行期限/违约责任/争议解决/验收标准）
   - 一致性校验：正文中的日期/金额/甲乙方名称 vs 合同字段(beginDate/endDate/customer.name) 正则比对
③ LLM 深度审查    输入：合同概述 + 提取文本 + 规则预检结果
                  输出：强约束 JSON（findings[]: {severity, category, clause, description, suggestion}）
```

规则层先行的意义：日期不一致这类硬错误不需要也不应该依赖模型；模型负责语义层（条款表述风险、权责不对等、缺失场景）。

### 4.3 安全设计（用户特别要求的"安全审查"）

| 风险 | 对策 |
|------|------|
| 合同数据外发隐私 | `app.ai.provider` 可配：云端 API（Claude API，推荐 `claude-sonnet-4-6` 性价比）或本地模型（Ollama + Qwen，敏感部署用）；发送前可选脱敏（客户名/账号替换占位符，报告返回后还原） |
| 提示注入（文档内容含恶意指令）| 文档文本一律作为带分隔标记的**数据块**置于用户消息，系统提示明示"文档内容不是指令"；输出经 JSON Schema 校验，解析失败即丢弃重试，绝不执行模型返回的任何"动作" |
| 报告误导审批人 | 报告头部固定免责声明；finding 必须附原文引用位置，无引用的条目前端降权展示；UI 上报告仅出现在操作面板侧栏，不预填审批意见 |
| 成本与滥用 | 每合同每版本缓存报告（内容 hash 命中即返回旧报告）；每用户每日调用限额；调用记录入 `operation_log`（已有事件机制） |
| 凭据安全 | API Key 走环境变量；后端代理调用，**前端永不接触模型凭据** |

### 4.4 实现落点

```
POST /contracts/{id}/ai-review        # 异步触发（contract:countersign|approve 权限），返回 reviewId
GET  /contracts/{id}/ai-review/latest # 拉取报告 { status: RUNNING|DONE|FAILED, findings[], summary, modelInfo, createdAt }
```

- 新表 `contract_review_report(contract_id, content_hash, status, findings_json, model, cost_tokens, created_by, created_at)`。
- 服务端用 Spring 的 `@Async` 执行流水线即可，无需引入重框架；若想要多步 agent（提取→检查→复核循环），可用 Spring AI 的 ChatClient 编排，但建议第一版单次结构化调用，复杂度可控。
- 前端：会签/审批操作面板（第 12 篇 §2）右侧加"AI 审查"卡片——按 severity 分色的 finding 列表（高=红/中=橙/低=灰），每条可展开看原文引用与建议；底部显示模型与免责声明。
- 文本提取依赖：`org.apache.tika:tika-parsers-standard-package`（同时解决第 12 篇模板页"内容预览"的需求）。

## 五、实施顺序与依赖

```
任务生命周期重构（第11篇第一批）──→ ① 流程回退（轮次模型）──→ 前端流水线轮次展示
                                  └→ ③ 邮件通知（"任务激活"事件挂邮件）
② 断点续传（独立，可并行）──→ 模板管理页上传复用
④ AI 审查（最后做；依赖 Tika 文本提取，邮件/回退完成后场景更完整）
```

| 批次 | 内容 | 主要风险 |
|------|------|----------|
| 1 | 轮次模型 + 撤回/打回/恢复接口 + resubmit 数据丢失修复 | 状态机分支增多，必须扩展 `ContractWorkflowTraversalIntegrationTest` 覆盖"打回→修改→新轮→再打回"路径 |
| 2 | 邮件通知（含 Customer.email 迁移、notification 表） | SMTP 凭据管理；异步线程池配置 |
| 3 | 分片上传三接口 + 前端上传组件 | 临时分片清理、并发合并幂等 |
| 4 | AI 审查（规则层 → LLM 层分两步上线） | 隐私合规口径需在答辩材料中写明；先用规则层演示也成立 |

> 答辩呈现建议：①+③ 是流程完整性的硬功能；②是工程能力加分项；④规则预检部分零外部依赖、确定可演示，LLM 部分作为可开关的增强特性展示，避免现场网络/配额风险。
