# 重构后全面代码审查（第三轮）

> 针对回退/轮次、模板文件、前端组件化三块重构后的代码，审查逻辑缺漏。
> 后端工作流核心由人工逐行审查 + 集成测试比对；前端交互与模板/安全由子 agent 并行审查后交叉验证。
> 结论先行：**回退/轮次状态机有两个会导致流程永久卡死的 P0**，且都未被现有集成测试覆盖。

## P0 — 流程永久卡死（最高优先级）

### P0-1. reject → resubmit 后无法签订，流程永久卡在"待签订"

**触发路径**：合同正常推进到 `FINALIZED` → 某审批人拒绝（`approve` result=REJECTED）→ 状态 `REJECTED` → 起草人修改 → `resubmit` → 第二轮审批全部通过 → 状态 `APPROVED` → **签订人无法签订**。

**根因**：任务创建时机不一致。`assign()`（[ContractService.java:94-96](backend/src/main/java/com/contractsys/contract/ContractService.java:94)）在分配时**一次性预创建** COUNTERSIGN / APPROVAL / SIGN 三类任务（round=1）。而拒绝-重提路径：
- `approve()` 拒绝分支只封存了 APPROVAL 任务：`supersedeCurrentRoundPendingTasksByType(contract, TaskType.APPROVAL, …)`（[ContractService.java:229](backend/src/main/java/com/contractsys/contract/ContractService.java:229)），SIGN 任务仍是 round-1 PENDING。
- `resubmit()` 把 `currentRound` 自增到 2，但**只克隆了 APPROVAL**：`cloneAssigneeTasksForNewRound(contract, previousRound, TaskType.APPROVAL, …)`（[ContractService.java:311](backend/src/main/java/com/contractsys/contract/ContractService.java:311)），没有克隆 SIGN。

结果：第二轮 APPROVED 后，`sign()` 调 `finishTask(… SIGN … contract.getCurrentRound())`（currentRound=2），但 SIGN 任务只存在于 round=1 → 抛 `403 当前用户没有该合同的待处理任务`；签订人的待办列表 `findActivePendingTasksByAssignee` 要求 `round = currentRound` 也查不到这条 → **既看不到待办也签不了，合同死在 APPROVED**。

**对比佐证**：`resume()` 的 FINALIZE 分支同时克隆了 APPROVAL **和** SIGN（[ContractService.java:171-172](backend/src/main/java/com/contractsys/contract/ContractService.java:171)），所以 RETURNED→resume 路径正常。唯独 `resubmit()` 漏了 SIGN——这是两套回退机制（REJECTED+resubmit 与 RETURNED+resume）并存导致的不一致。

**测试盲区**：`rejectionAndResubmitLoopResetsApprovalTasks`（[测试:196-230](backend/src/test/java/com/contractsys/contract/ContractWorkflowTraversalIntegrationTest.java:196)）在 `assertStatus(id, "APPROVED")` 处结束，**从未在 resubmit 后调用 sign**，正好停在 bug 触发点之前。

**修复方向**（二选一）：
- 快速修：`resubmit()` 增补 `cloneAssigneeTasksForNewRound(contract, previousRound, TaskType.SIGN, "contract:sign")`。
- 治本修：废弃 REJECTED+resubmit，审批拒绝统一走 RETURNED + `resume`（与"打回"合并为一条回退机制）。
- 无论哪种，补一条 `reject → resubmit → approve → sign → SIGNED` 的端到端测试断言。

### P0-2. withdraw（撤回任务）对定稿/审批环节会让流程永久卡死

**触发路径 A（撤回定稿）**：合同到 `FINALIZED` → 起草人 `withdrawTask` 撤回定稿 → 状态回 `COUNTERSIGNED` → 起草人重新定稿 → `FINALIZED` → **审批人无任务可审**。

**触发路径 B（撤回审批）**：合同到 `APPROVED` → 某审批人 `withdrawTask` 撤回审批 → 回 `FINALIZED` → 重新审批通过 → `APPROVED` → **签订人无任务可签**。

**根因**：同 P0-1 的预创建机制。`rewindStatusForWithdraw()`（[ContractService.java:459-475](backend/src/main/java/com/contractsys/contract/ContractService.java:459)）在回退时会 **封存下一环节的预创建任务**：
- 撤回 FINALIZE → `supersedeCurrentRoundPendingTasksByType(…, APPROVAL, …)` 封存了 assign 时预建的 APPROVAL 任务；
- 撤回 APPROVAL → 封存了预建的 SIGN 任务。

但前进路径不会重建它们：`finalizeContract()` 不创建 APPROVAL 任务（它们本应在 assign 时就存在），`approve()` 也不创建 SIGN 任务。于是重新定稿/审批后，下一环节的任务已被封存且无人重建 → 永久卡死。

**为何 COUNTERSIGN 撤回不受影响**：FINALIZE 任务是"按需创建"的（在 `countersign()` 全部完成时才建，[ContractService.java:109](backend/src/main/java/com/contractsys/contract/ContractService.java:109)），所以撤回会签→重新会签会重新触发 FINALIZE 创建。**根本矛盾在于：FINALIZE 按需创建，而 APPROVAL/SIGN 在 assign 时预创建——两种时机混用，撤回逻辑只对按需创建的那类成立。**

**测试盲区**：`withdrawTask` 端点**没有任何测试覆盖**（全仓库搜索 withdraw 只命中 Controller/Service 定义）。

**修复方向**：统一任务创建时机。推荐"全部按需创建"——APPROVAL 在 `finalizeContract()` 完成时创建，SIGN 在 `approve()` 全通过时创建；这样 `rewindStatusForWithdraw` 的封存逻辑对所有环节自洽，也顺带让 P0-1 一并消失（前进时总会重建当前轮任务）。这是比逐个打补丁更彻底的方案。

### P0-3. 前端"撤回任务"按钮无权限校验、显示条件比后端宽（子 agent 发现，已核对）

`canWithdrawCurrent`（[ContractDetailView.vue:422](frontend/src/views/ContractDetailView.vue:422)）只判断"本人 + 当前轮 + 任务 DONE/REJECTED"，**完全没有 `hasPermission` 判断**，也没有对照后端 `ensureWithdrawAllowed`（[ContractService.java:444](backend/src/main/java/com/contractsys/contract/ContractService.java:444)）的链式约束（SIGN 不可撤、已签订不可撤、下一环节已完成不可撤）。结果：按钮在不该出现时照常出现，用户点了必然吃 409。需补权限校验 + 镜像后端约束。

> 注：P0-2（后端真卡死）与 P0-3（前端误导按钮）叠加后体验更糟——用户被引导去点一个既会报错、即使"成功"也会让合同卡死的操作。两者应一起修。

## 整改优先级

1. **P0-1 + P0-2 一并治本**：统一任务创建时机为"全部按需创建"（APPROVAL 在定稿后建、SIGN 在审批通过后建），同时消除 reject/resubmit 与 withdraw 两类卡死；补 `reject→resubmit→sign` 与 `withdraw→重做→后续环节` 两条端到端测试。
2. **P0-3 + P1-4/5/6/8**：前端流水线与待办在多轮次/打回场景下的展示与按钮门控修正（与后端回退语义对齐）。
3. **P1-1/P1-2**：模板可见范围补齐 + 缓存归属厘清。
4. **P1-7、P2 批量**：编辑状态对齐、死代码清理、JWT fail-fast、权限刷新策略。

> 核心教训：本轮回退/轮次重构的所有卡死问题，根源都是**同一个**——APPROVAL/SIGN 在 assign 时预创建，而 FINALIZE 按需创建，两种时机混用使得"轮次推进"和"撤回封存"两套机制只对其中一类成立。统一创建时机后，绝大多数 P0/P1-后端项会一并消失。重构前建议先补齐回退路径的端到端测试，再动刀。
